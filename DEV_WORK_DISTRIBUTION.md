## 1. Как работать безопасно параллельно через GitHub (Zero Conflicts)

Главная опасность параллельной работы — когда два разработчика одновременно меняют одни и те же крупные файлы (например, `ResultScreen.jsx`, `MedSimApp.jsx` или `scoring.js`). Чтобы избежать конфликтов слияния:

1. **Разделение зон ответственности по файлам (Zero Overlap):**
   Каждый разработчик работает **только в своих директориях и файлах**.
2. **Feature-ветки от `main`:**
   Никто не пушит напрямую в `main`. Создаются ветки:
   - Разработчик 1: `git checkout -b feat/ui-redesign-results`
   - Разработчик 2: `git checkout -b feat/gastro-ai-patient-scoring`
3. **Единый контракт интерфейсов (Phase 0):**
   Договариваемся о форматах данных (props и структуры объектов) до написания UI. Разработчик 1 верстает компоненты под этот контракт, Разработчик 2 наполняет данные и движок под этот же контракт.
4. **Синхронизация через Pull Requests:**
   Перед мерджем подтягиваем актуальный `main` через `git fetch origin && git rebase origin/main` (или `git merge origin/main`), проверяем сборку `npm run build` и тесты `npm run test`.

## 2. Матрица разделения файлов и зон ответственности

| Зона ответственности | Разработчик 1 (Frontend & UI/UX) | Разработчик 2 (Core, Data & AI) |
| :--- | :--- | :--- |
| **Основной фокус** | Редизайн игрового экрана + Новый экран результатов (без свалки) + Декомпозиция UI | Специальность «Гастроэнтерология» + ИИ-пациент (гибрид) + Движок скоринга ошибок |
| **Папки работы** | `src/screens/game/`<br>`src/screens/ResultScreen.jsx`<br>`src/components/result/`<br>`src/ui/` | `src/data/cases/gastroenterology/`<br>`src/data/cases/index.js`<br>`src/engine/`<br>`src/services/` |
| **Точки соприкосновения** | Читает данные кейсов и результат скоринга | Предоставляет структуру данных кейсов и объект `result` |

> **Правило:** Если Разработчику 1 требуется изменить структуру данных кейса, он сообщает Разработчику 2. Если Разработчику 2 требуется вывести новую кнопку в UI, он передает контракт/пропс Разработчику 1 или создает изолированный переиспользуемый компонент.

  - Новые декомпозированные компоненты в `src/components/game/`

### Задача 1.2. Полная пересборка экрана результатов (`ResultScreen`)
* **Проблема сейчас:** Экран перегружен, более 15 разрозненных блоков («навалено куча всего»), дублируются тесты, назначения, патофизиология и ИИ-замечания.
* **Решение:**
  - Организовать экран по **вкладкам (Tabs)** или четким смысловым секциям:
    1. **Вкладка 1: «Клинический итог»** — итоговый балл, исход пациента, дельта витальных показателей, верность диагноза.
    2. **Вкладка 2: «Разбор ошибок и КР»** — единый структурированный список ошибок (пропущенные тесты, противопоказанные препараты, дефекты анамнеза, комментарий ИИ) без повторений, с подсказками по клиническим рекомендациям.
    3. **Вкладка 3: «Обоснование и теория»** — патофизиология, ссылка на КР РФ, связанные темы теории, чек-листы.
    4. **Вкладка 4: «Хронология действий»** — таймлайн принятых врачом решений (EventLog).
* **Файлы:**
  - `src/screens/ResultScreen.jsx`
  - `src/components/result/*` (декомпозиция на модульные вкладки: `ResultSummaryTab.jsx`, `ResultErrorsTab.jsx`, `ResultTheoryTab.jsx`, `ResultTimelineTab.jsx`).

### Задача 1.3. Декомпозиция UI-компонентов
* Разбить монолитные экраны на небольшие компоненты (до 150-200 строк).
* Вынести повторяющиеся карточки, бейджи, модалки в `src/ui/` или `src/components/`.

## 5. Пошаговый сценарий работы для обоих разработчиков (Git Cheatsheet)

### Шаг 1. Актуализация локального репозитория
Оба разработчика выполняют:
```bash
git checkout main
git pull origin main
```

### Шаг 2. Создание персональных веток
* **Разработчик 1:**
  ```bash
  git checkout -b feat/ui-redesign-results
  ```
* **Разработчик 2:**
  ```bash
  git checkout -b feat/gastro-ai-patient-scoring
  ```

### Шаг 3. Ежедневная разработка и локальные коммиты
Коммитить часто с понятными сообщениями по Conventional Commits:
```bash
git add .
git commit -m "feat(ui): implement tabbed layout for ResultScreen"
# или
git commit -m "feat(cases): add acute pancreatitis case for gastroenterology"
```

### Шаг 4. Подтягивание изменений (если кто-то уже смерджил в main)
Если один разработчик влил PR в `main`:
Второй разработчик в своей ветке делает:
```bash
git fetch origin
git merge origin/main   # или git rebase origin/main
npm run build           # убедиться, что проект компилируется без ошибок
git push origin <ваша-ветка>
```

### Шаг 5. Создание Pull Request
На GitHub открывается Pull Request в ветку `main`, проводится код-ревью коллегой и нажимается «Merge».
