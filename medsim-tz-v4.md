# МЕДСИМ — Техническое задание 

**Основание:** обсуждение по итогам `otchet-analiz-v4.md` — медицинский аудит, новая механика Поликлиники, ревизия справочников диагностики/лечений. Дополняет ТЗ v3/v4, не заменяет их.

**Как читать:** как и в предыдущих версиях — максимально буквально, без додумывания. Там, где правка касается конкретных `caseId`, они перечислены явно, списком, а не общей фразой «где нужно».

## Блок У. Ревизия справочника диагностики

### FR-У.1. Удаление `tsh`

Поле `tsh` («ТТГ / Т4 свободный, отдельный») удаляется из справочника диагностики полностью. Везде, где `tsh` встречается в `needDiag` какого-либо кейса, заменяется на `thyroid`.

### FR-У.2. Удаление `lipid`

Поле `lipid` (липидный профиль) удаляется из справочника диагностики полностью. Кейсы 1, 3, 36, 37 (где он упоминался в контексте «никогда не используется») **не должны** получать этот тест взамен — просто убрать поле из справочника, в `needDiag` этих кейсов оно и так отсутствовало.

### FR-У.3. Удаление `bedside_usg`, слияние с `echo`/`usg_abdo`

Поле `bedside_usg` удаляется из справочника диагностики. Вместо него в кейсах, где FR-У.6 требует «добавить POCUS», используется:
- **`echo`** — для кейсов с кардиальным контекстом: **4, 39, 40**;
- **`usg_abdo`** — для кейсов с абдоминальным контекстом: **13, 31, 32**.

### FR-У.4. Разделение `crp` на два теста

Поле `crp` («СРБ / Прокальцитонин») разделяется на два независимых теста:
```
crp: { id: "crp", name: "СРБ (С-реактивный белок)", category: "lab" }
procalcitonin: { id: "procalcitonin", name: "Прокальцитонин", category: "lab" }
```
Во всех кейсах, где ранее использовался `crp`, необходимо вручную решить, какой из двух (или оба) реально нужен по клиническому смыслу кейса — **это требует ручного прохода по каждому такому кейсу**, автоматической замены 1:1 недостаточно, так как раньше это был один тест, а не два независимых.

### FR-У.5. `culture` — не трогать

Поле `culture` («Посев крови / мочи») оставить как есть, без разделения — оба посева служат одной диагностической цели, разделение не даёт практической пользы для геймплея.

### FR-У.6. Добавление отсутствующей диагностики — точный список по кейсам

| Тест | Кейсы, куда добавить в `needDiag` |
|---|---|
| `lactate` | 1, 2, 8, 11, 12, 13, 14, 15, 16, 18, 20, 26, 28, 32, 33, 37, 43, 44, 50, 51, stat_1, stat_2, stat_3, stat_5 |
| `echo` (замена POCUS, см. FR-У.3) | 4, 39, 40 |
| `usg_abdo` (замена POCUS, см. FR-У.3) | 13, 31, 32 |
| `tox_screen` | 26, 27, 28, 29, 30 |
| `type_cross` | 32, 45, stat_4 |
| `eeg` | 6, 51 — **добавить уверенно** (есть прямая опора в клинической рекомендации по эпилепсии/эпилептическому статусу); 10, 53 — добавить с пометкой в реестре ревью «сверить отдельно при К.5–К.8» (правдоподобно, но не подтверждено независимо на момент написания этого ТЗ) |
| `coag_full` | stat_2, 32 |

**Критерий приёмки Блока У:** после правок в справочнике диагностики отсутствуют `tsh`, `lipid`, `bedside_usg`; `crp` заменён на `crp`+`procalcitonin` с ручной разметкой по каждому затронутому кейсу; все позиции из таблицы FR-У.6 присутствуют в `needDiag` указанных кейсов.

## Блок Ф. Ревизия справочника лечений

### FR-Ф.1. Удаление `dantrolene`

Поле `dantrolene` удаляется из справочника лечений полностью — решено не создавать под него отдельный кейс (нишевое показание, злокачественная гипертермия, не входит в текущий охват специальностей).

### FR-Ф.2. Слияние `steroids` и `methylprednisolone`

Два поля объединяются в одно:
```
steroids: { id: "steroids", name: "Кортикостероиды в/в", effects: { spo2: 5, hr: -5 }, delay: 90 }
```
Поле `methylprednisolone` удаляется из справочника. Везде, где `methylprednisolone` встречался в `needTreat`/`wrongTreat` какого-либо кейса, заменяется на `steroids`.

### FR-Ф.3. `captopril` — не заводить, использовать существующий `ACE_inhibitor`

Отдельная сущность `captopril` **не создаётся**. Правка `outp_1` (см. Блок Т) использует уже существующий `ACE_inhibitor`.

### FR-Ф.4. `gastric_lavage` — переопределение роли

Поле остаётся в справочнике, но **не добавляется как обязательное** (`needTreat`) ни в один из токсикологических кейсов (26–30). Допустимо использовать его как `wrongTreat` в кейсах, где его применение было бы избыточным/рискованным по современным рекомендациям (конкретные кейсы для такой пометки — на усмотрение при ревью, не являются обязательным требованием этого ТЗ).

### FR-Ф.5. Добавление лечений — точный список по кейсам

| Лечение | Кейсы, куда добавить |
|---|---|
| `naloxone` | Кейс опиоидного отравления среди 26–30 (конкретный `caseId` определяется по содержанию кейса — тот, где отравляющее вещество — опиоид) |
| `activated_charcoal` | Кейсы пероральных отравлений с ранним обращением среди 26–30 |

### FR-Ф.6. Осознанно оставить неиспользуемыми (без правок)

`dopamine`, `magnesium`, `ketamine` — остаются в справочнике, не добавляются ни в один кейс в рамках этого ТЗ. Причина по каждому:
- `dopamine` — современные рекомендации ставят норадреналин выше дофамина в большинстве шоковых состояний, специально добавлять не нужно;
- `magnesium`, `ketamine` — требуют кейсов (torsades/преэклампсия/тяжёлая астма; травматологический кейс), которых сейчас нет в библиотеке — не создаются в рамках этого ТЗ, остаются заделом на будущее расширение контента.

**Критерий приёмки Блока Ф:** `dantrolene` отсутствует в справочнике; `methylprednisolone` отсутствует, все его прежние вхождения заменены на `steroids`; `naloxone`/`activated_charcoal` присутствуют в соответствующих кейсах отравлений; `gastric_lavage` не встречается ни в одном `needTreat`.

## Блок Т. Медицинские правки конкретных кейсов

Каждая правка ниже — точная, с указанием, что именно меняется в `needDiag`/`needTreat`/`wrongTreat`. Все указанные кейсы после применения правок возвращаются в реестр ревью со статусом `pending` и требуют повторного прохождения по чек-листу (К.2) прежде, чем получить `reviewed`.

### FR-Т.1. Кейс 4 (тампонада сердца)
Добавить `pericardiocentesis` в `needTreat`.
Добавить `echo` в `needDiag` (см. FR-У.6/FR-У.3).

### FR-Т.2. `outp_1` (гипертонический криз)
Удалить `iv_fluids` из `needTreat`.
Добавить `ACE_inhibitor` в `needTreat` (см. FR-Ф.3).
`metoprolol` — **оставить** в `needTreat` как один из допустимых вариантов (не единственно верный, но клинически приемлемый при кризе с тахикардией).

### FR-Т.3. `outp_4` (ХСН II ФК)
Удалить `iv_fluids` из `needTreat`.
`furosemide` и `metoprolol` — оставить без изменений.

### FR-Т.4. `outp_3` (гипотиреоз)
Удалить `iv_fluids` из `needTreat`.
Добавить `thyroxine` в `needTreat`.

### FR-Т.5. Кейсы 10, 53 (ВПГ-энцефалит)
Удалить `steroids` из `needTreat`.
Кейс 54 (аутоиммунный энцефалит) — **не трогать**, там `steroids` клинически обоснован.

### FR-Т.6. 19 кейсов с `oxygen` при нормальной SpO₂
Точный список кейсов — определяется по тем же критериям, что использовал медицинский аудит (SpO₂ ≥ 95% на старте кейса). Правка: `oxygen` **не удаляется** из кейса полностью — убирается только из `needTreat` (перестаёт быть обязательным, штрафуемым при пропуске пунктом), при этом остаётся доступным действием в интерфейсе кейса и не помечается как `wrongTreat`.

### FR-Т.7. `outp_2` (хронический холецистит)
Удалить `antibiotics_broad` из `needTreat`.

### FR-Т.8. Кейс 12 (обострение ХОБЛ)
**Не удалять** `antibiotics_broad` напрямую. Вместо этого — добавить в данные кейса поле анамнеза (см. Блок Р из ТЗ v4, `historyOfIllness`) явное указание на характер мокроты. Если по сценарию кейса мокрота гнойная — `antibiotics_broad` остаётся обязательным; если нет — убирается из `needTreat`. Конкретное клиническое решение (гнойная/негнойная) принимается при ревью, не задаётся этим ТЗ директивно.

**Критерий приёмки Блока Т:** каждый из перечисленных `caseId` после правки не содержит удалённых пунктов и содержит добавленные; все перечисленные кейсы имеют статус `pending` в реестре ревью до момента прохождения повторного ревью.

## Блок С. Новая механика Поликлиники

### FR-С.1. Удаление таймера и детериорации

`OutpatientGameScreen`/`useOutpatientCycle` (или аналогичный существующий хук) лишается любой логики автоматического ухудшения состояния и обратного отсчёта времени. Исход «смерть» для отделения `outpatient` **не существует** — это прямо возвращает соответствие FR-3.4.2 из исходного ТЗ v1.

### FR-С.2. Виталы скрыты по умолчанию

При открытии кейса `outpatient` витальные показатели **не отображаются** сразу. Вместо таблицы виталов — кнопка **«Провести осмотр»**.

### FR-С.3. Раскрытие по клику

Клик по «Провести осмотр» открывает список доступных измерений (АД, ЧСС, температура, SpO₂ и т.д. — по аналогии с уже существующим списком `needDiag`). Игрок выбирает, какие именно измерения произвести — каждое измеренное значение становится видимым, невыбранные остаются скрытыми.

### FR-С.4. Значения не «протухают»

В отличие от ранее обсуждавшегося варианта с истечением актуальности — **этот вариант не реализуется**. Однажды измеренное значение остаётся видимым как есть, без необходимости повторного измерения после лечения, без пометок «устарело».

### FR-С.5. Завершение кейса

Кейс завершается решением о маршруте (`route`, см. Поликлинику из исходного ТЗ v1 — `лечить амбулаторно`/`направить к специалисту`/`направить на плановую госпитализацию`/`вызвать СМП немедленно`), доступным в любой момент прохождения, не привязанным к таймеру, поскольку таймера больше нет.

**Критерий приёмки Блока С:** кейс Поликлиники не имеет исхода «смерть»; виталы не отображаются до клика «Провести осмотр»; после лечения ранее измеренные значения остаются видимыми без дополнительных действий игрока.

## Блок Х. Прочие исправления

### FR-Х.1. Баг повторного туториала

Запуск обучающего кейса из М.2 (ТЗ v3) должен происходить **только** при первом входе в приложение или по явному выбору пункта «Обучение» в меню (М.4). Переход на `MenuScreen` после завершения обычного кейса **не должен** повторно запускать туториал. Проверить, что состояние «туториал уже пройден» (аналогично `seenTutorial` из М.3) действительно проверяется перед автозапуском, а не только при первом вызове компонента.

### FR-Х.2. Удаление фильтра «Все экстренные»

Фильтр «Все экстренные» удаляется из `MenuScreen` полностью. Остаются только раздельные фильтры «ОРИТ» и «Приёмное» (плюс уже существующие «Поликлиника»/«Стационар»).

### FR-Х.3. UX-правки

- Боковая панель меню — исправить прокрутку (содержимое, не помещающееся на экран, должно быть доступно скроллом).
- Список препаратов в `StationaryGameScreen` — привести к визуальному виду, аналогичному списку в ОРИТ (тот же компонент/стиль отображения).
- Чек-лист Assessment mode — перевести оставшиеся англоязычные строки на русский полностью.
- Подсказки обучающего режима (М.2 из ТЗ v3) — расширить содержание каждой из 7 подсказок, добавив больше конкретики (не просто «это индикатор времени», а объяснение, как именно на него реагировать).
- Анамнез в Стационаре — отображать по центру экрана в момент начала дня, затем перемещать в обычное постоянное место интерфейса.
- Анамнез в Поликлинике — увеличить визуальный размер блока отображения.

### FR-Х.4. Мини-теория для кейсов Стационара вне Curriculum mode

Для каждого кейса `stationary` добавляется краткий теоретический блок (доступный из интерфейса кейса или дебрифинга — не обязательно полноценный `TheoryScreen`), поясняющий ключевые моменты по данной нозологии, аналогично блоку «Источники» из Н.3 (ТЗ v3), но не требующий прохождения Curriculum mode для доступа.

### FR-Х.5. Проверка гейта видимости в продакшн-условиях

Провести ручную проверку: собрать приложение с `IS_DEV_MODE=false`, убедиться, что кейсы со статусом `pending` в реестре ревью действительно не отображаются ни в одном списке (свободный выбор, Curriculum mode, Assessment mode). Результат проверки — не «работает», а конкретный пример: какой `caseId` был `pending`, что он не появился в списке, каким способом это проверялось.

**Критерий приёмки Блока Х:** каждый из пяти FR выше проверен отдельно, с конкретным примером/скриншотом, а не общим утверждением о завершении.

## Definition of Done для ТЗ 

1. Справочники диагностики и лечений приведены в соответствие Блокам У/Ф — дубли устранены, отсутствующие пункты добавлены по точным спискам.
2. Все кейсы из Блока Т исправлены, возвращены в `pending` и повторно проведены через ревью (К.2) до статуса `reviewed`.
3. Поликлиника полностью соответствует FR-3.4.2 (без таймера, без исхода «смерть», виталы по требованию).
4. Баг повторного туториала исправлен, фильтр «Все экстренные» удалён, перечисленные UX-правки внесены.
5. Мини-теория присутствует у каждого кейса Стационара.
6. Гейт видимости подтверждён работающим в продакшн-режиме конкретным проверенным примером, а не утверждением на веру.
